# 11 · 数据安全扫描 = 版本级发布门 设计

## 1. 背景与需求关联

端到端流程(数据工程视角):`原始数据源 → 数据接入 → 原始数据湖(多版本) → [安全扫描 / 质量评估 / 加工 / 标注] → 数据集仓库发布 → 算法工程师选训练集`。

该 6 步流程是知识库文章的**叙事综合**,不是原始需求的逐条。但本设计有明确的需求支点:

| 需求 | 评分方式 | 与本设计的关系 |
|------|----------|----------------|
| **#4 数据内容安全** | **通过性指标(pass/fail)** | 评分方式天然是"闸门"——这是把内容安全做成**发布门**的正当性来源 |
| #11 数据血缘 | 完整性 | 门控转换、产物版本均经 `produced_by_job_id` / `JobInput` 可溯源 |
| #13 元信息 / #15 分级 / #19 生命周期 | — | "数据集仓库发布"环节的配套动作,发布门是它们的前置 |
| #5 访问安全 | 通过性指标 | 发布 / 下架 / 人工覆盖均为写操作,`require_admin` + 审计 |
| #17 版本 / #18 托管 | 完整性 | 发布状态、扫描结论均**绑定到版本**(不可变版本链) |

**现状缺口**:内容审核(#4)、脱敏(#7 加工算子)、分级(#15 元信息)三件事**散在三处**,内容安全只是与质量/加工平级的任务、无任何顺序约束;`datasets` 表也**没有"发布/入仓"状态**。本设计把它们串成一道发布门。

## 2. 设计决策(已对齐)

1. **数据安全扫描做成前置门**(治理"未过不许往下走")。
2. **门控力度 = 只卡发布**:质量/加工/标注在草稿版本上自由跑,只有"发布为可训练/入仓"被卡。
3. **引入"发布/入仓"状态**(湖→仓边界):平台原本数据集扁平、无发布概念。
4. **版本级发布**:发布/下架作用在具体 `DatasetVersion` 上,贴合不可变版本 + 血缘。
5. **通过判定 = 自动判定 + 人工可覆盖**:默认按阈值自动判,有权限者可人工接受风险/驳回。

## 3. 数据模型(迁移 `0010`,down_revision=`0009_categories`)

**仅给 `dataset_versions` 加列,不新增表**:

| 列 | 取值 | 默认 | 说明 |
|----|------|------|------|
| `scan_verdict` | `unscanned` / `passed` / `failed` | `unscanned` | 安全扫描结论(展示:未扫描 / 通过 / 未通过) |
| `verdict_source` | `auto` / `manual` / `null` | `null` | 结论来源:自动判定 or 人工覆盖 |
| `verdict_note` | text / null | `null` | 人工覆盖理由(接受风险 / 驳回) |
| `publish_status` | `draft` / `published` / `unpublished` | `draft` | 发布状态(草稿 / 已发布 / 已下架) |
| `published_at` | datetime / null | `null` | 发布时间(可追溯) |

- 自动判据复用既有 **`review_findings`**(已有 `severity` / `category` / `source`);**人工覆盖**写既有 **`audit_logs`**(#5),不新建审计表。
- 迁移仅 `add column` + 默认值,**无回填风险**;存量版本自动落 `unscanned` / `draft`。

## 4. 通过判定(自动 + 人工可覆盖)

**结论挂在内容审核的产出(打标)版本上**:review 任务扫描输入版本 → 产出 `origin=review`
的打标新版本,该版本**出生即带 `scan_verdict`**。其它来源(接入/加工)的版本默认
`unscanned`,必须先跑一次内容安全扫描、用其打标产物去发布——"扫描前置"由此落地。

- **自动判据(实现口径,三态)**:据 `scan_version` 返回的 `report`——
  - `flaggedRows > 0` → **`failed`**
  - `flaggedRows == 0` 且 `sampleLimitApplied`(只扫了样本前缀)→ **`unscanned`**(未完整覆盖,不自动通过;需调大 `sampleLimit` 全量重扫或人工接受风险)
  - `flaggedRows == 0` 且全量扫描 → **`passed`**(`verdict_source=auto`)
  > 取"零命中=通过"而非"高危=0":引擎里敏感词/正则/关键词命中为 `medium`、PII 为
  > `low`、仅 LLM 可判 `high`;若按"高危=0"则 PII/敏感词会漏过门。且 `passed` **必须意味着
  > 整版扫过且干净**——否则尾部 PII 会借默认 `sampleLimit=500` 的部分扫描从门漏过。
- **人工覆盖**:`require_admin` 对某版本设 `passed`(接受风险)或 `failed`(驳回),附
  `verdict_note`,经 #5 审计中间件留痕(target 记 version_id);`verdict_source=manual`,**优先于自动结论**。
  驳回(`failed`)一个**已发布**版本时,同时将其 `unpublish`(维持不变量「已发布 ⟹ 通过」)。
- **重扫**:对新版本重跑内容安全 → 产出带新 `scan_verdict` 的打标版本(auto)。

## 5. 发布门(只卡发布)

- 新增**版本级发布 / 下架** API(`require_admin`):
  - `POST /datasets/{id}/versions/{vid}/publish` —— 校验目标版本 `scan_verdict == passed`,否则 **409** + 文案(提示走脱敏闭环);通过则 `publish_status=published` + `published_at`。
  - `POST /datasets/{id}/versions/{vid}/unpublish` —— `published → unpublished`。
- **状态机**:`draft --(门: scan_verdict=passed)--> published --(下架)--> unpublished --(重发)--> published`。
- **只卡发布**:质量 / 加工 / 标注 在 `draft` 版本上**不受限**;`unscanned ≠ passed` ⟹ 没扫过的版本发不出去 = "扫描前置"自然成立。

## 6. 脱敏闭环(复用现有件,不新建功能)

```
版本 failed(命中高危/PII) → 数据加工挂隐私脱敏算子(删IP / 人脸模糊 / LLM redaction)
   → 产出新版本(draft) → 对新版本重跑安全扫描 → passed → 方可发布
```

这条路径把「检测(#4)」与「脱敏(#7)」用发布门串成闭环,无需新增功能。

## 7. 后端改动点

- **模型 + 迁移 `0010`**:`dataset_versions` 加 §3 五列。
- **`review_runner`**:任务完成后按阈值计算并回写本版本 `scan_verdict`(`verdict_source=auto`)。
- **新 API**(挂 `content_safety` 或 `datasets` 路由):发布 / 下架 / 人工覆盖 verdict;均 `require_admin` + 审计。
- **`DatasetVersionRead`**:新增 `scanVerdict` / `verdictSource` / `publishStatus` / `publishedAt` 字段。
- **消费侧过滤**:训练集/数据集选择处可按 `publish_status=published` 过滤(算法工程师只见已发布)。

## 8. 前端改动点

- **版本列表 / 数据集详情**:展示「扫描结论」+「发布状态」徽章(复用 `versionLabel` 同款样式)。
- **发布 / 下架按钮**(admin 门控)+ 人工「接受风险 / 驳回」入口(附理由)。
- 发布失败(409)→ 提示脱敏闭环路径(跳数据加工挂隐私脱敏算子)。

## 9. 不破坏现网

- 两个状态默认值(`unscanned` / `draft`)→ 存量版本与现有 接入/加工/质量/审核 流程**完全不受影响**。
- 门只在**新的"发布"动作**上生效;不发布则一切照旧。
- 迁移纯 `add column`,可安全回滚。

## 10. 范围 / 非目标

- 本设计仅覆盖 **内容审核 → 脱敏 → 版本级发布门** 这条线。
- **分级分类自动化**(扫描反哺密级建议)= 后续;当前分级仍人工(#15 已实现的元信息)。
- **数据标注(#12)** 规划中,不在本设计。
- 数据集级"发布"汇总视图(是否有已发布版本)= 可选增强,本期不做。

## 11. 风险 / 取舍

- 自动阈值可能误判(漏报/误报)→ **人工覆盖兜底**,且覆盖留审计。
- "只卡发布"不阻止草稿区流转 → **刻意接受**:与"加工=脱敏手段"不矛盾(若卡全部下游会自相矛盾)。
- `scan_verdict` **绑版本、不继承**:加工产新版本后必须重扫——保证诚实,代价是多跑一次扫描。
- **不变量**:`published ⟹ scan_verdict=passed`。发布门 + 「驳回已发布版本即下架」共同维持;
  下架仅允许对 `published` 版本(否则 409),发布幂等(不改写首次 `published_at`)。
- **审计粒度(demo 级)**:每次 publish/unpublish/verdict 经审计中间件落一条 `audit_logs`
  (who/when/method/path,target=version_id)。人工接受风险的**理由**存版本列 `verdict_note`
  (可被后续覆盖、非 append-only);完整的判决历史表留作后续增强,当前不做。

## 12. 验收

- 对 `unscanned` / `failed` 版本调发布 → 被拒(**409** + 脱敏闭环提示)。
- `passed` 版本可发布;`published` 版本可被算法侧按 `publish_status` 选用。
- 人工「接受风险」后可发布,且 `audit_logs` 有记录;「驳回」后不可发布。
- 脱敏产新版本 → 重扫 `passed` → 可发布(端到端闭环跑通)。
