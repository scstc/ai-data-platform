# 数据集可溯源可复现——现状评估与整改方案

## 0. 需求

> 可以查看数据集的**来源任务**,以及任务所涉及到的**所有资产信息**,保证数据集**可溯源、可复现**。

拆成两个可判定标准:

- **可溯源(traceable)**:从任一数据集版本,能查到「产出它的任务」+「任务消费的全部资产」+ 递归回溯到最初来源(数据源/上传)。
- **可复现(reproducible)**:能用同样的输入 + 同样的算子/参数 + 同样的模型,重跑得到同样(或配方级一致)的结果。

**结论:当前不完全满足。** 只对「纯算子加工、且数据经数据湖入库」的数据集基本能做到溯源+复现;其余四类场景(直连上传/媒体、两跳湖搬运、用 LLM 的任务、出湖抽取)均有硬缺口,其中「可复现」对用 LLM 的任务**无法保证**。

---

## 1. 现状全景:数据到数据集的三条腿

```
【第一腿:入湖 / 直落】
 DataSource ──IngestTask(建 Job type=ingest)──► 连接器 run_ingest
   │                                              │ if task.lake_id:
   │                                              ├─► ingest_to_lake_parquet/raw ─► DataLakeSnapshot(不可变)
   │                                              │       (datasource_id/ingest_task_id/job_id/merge_inputs)
   │                                              └─► else: add_table_member 直落数据集(无来源血缘)
   │
【第二腿:出湖抽取】  POST /data-lakes/{id}/extract-to-dataset  (可多选 snapshot_ids)
   └─► extract_to_new_dataset ──(不建 Job)──► add_table_member(source_snapshot_id=快照)
                                                         └─► DatasetVersionTable ─► DatasetVersion
【第三腿:加工产版本】  POST /jobs ─► job_runner 按 type 分发
   输入版本 v(n) ──► run_process_job [.staging 两阶段 + dj-process 子进程]
                    ──► 新版本 v(n+1)  produced_by_job_id=job_id + JobInput(job_id, v(n))
```

关键事实(逐文件核实):

- **加工任务的 version↔job 血缘是填满的**:所有产版本的任务都在同一事务写 `JobInput(job_id, dataset_version_id)`(`engine.py:980`)并在版本上钉 `produced_by_job_id=job_id`(`engine.py:938`)。
- **算子配方进 spec**:`Job.spec.operators`(名+参数)可 rerun(`job_runner.body_from_spec`)。
- **数据不可变**:湖快照、数据集版本、版本成员均不可变,加工 staging 自包含(`engine.py:747` 版本间零共享)——这是「复现-数据」这一半的坚实基础。

---

## 2. 「任务所涉及的所有资产」——五类资产判定矩阵

一个加工任务真正牵涉的资产分五类。现状:

| 资产类别 | 是否记录 | 能否查看 | 是否固化(复现用) | 判定 |
|---|---|---|---|---|
| **输入数据**(输入版本+成员) | ✅ `JobInput` | △ 仅版本级 | ✅ 版本不可变 + staging 自包含 | 溯源△ 复现✅ |
| **上游来源**(湖快照→湖对象→数据源) | △ 仅湖路径有 `source_snapshot_id` | ❌ 入湖 Job 不进图、出湖无 Job | ✅ 快照不可变 | 部分 |
| **算子链**(名+参数) | ✅ `Job.spec.operators` | ✅ 图上 job 节点 | ✅ 显式参数进 spec | ✅ |
| **模型资产**(供应商/模型/端点) | ❌ **运行时解析,不进 spec** | ❌ | ❌ **重跑用当时激活配置** | ✗ 复现失败 |
| **产出**(输出版本+成员) | ✅ `produced_by_job_id` | ✅ | ✅ | ✅ |

---

## 3. 阻断「可溯源」的缺口

1. **直连旁路的数据集完全无来源可查(最严重)。** `POST /datasets/upload-batch`、API push(`land_push_records`)、遗留直采(`task.lake_id` 为空)都不传 `source_snapshot_id`,成员来源字段永远 NULL,血缘图直接过滤(`datasets.py:1114` `snap_ids = {m.source_snapshot_id ... if m.source_snapshot_id}`)。这类数据集连「从哪来」都答不出。

2. **媒体数据断链。** 图片/音视频走 `land_media_manifest`(`lake_extract.py:449`)绕过 `add_table_member`,即便来自湖也不写来源快照。

3. **两跳湖搬运是「匿名」的。**
   - **入湖跳**:`ingest` Job 存在(`ingest_tasks.py:678`)、`job_id` 也盖在快照上,但血缘图湖层只画 `datasource→snapshot`,不画这个 Job → 查不到「哪个采集任务/连接器、何时」拉进湖。
   - **出湖跳**:抽取**根本不建 Job**(`lake_extract.py` 不 import Job,`produced_by_job_id` 保持 None,靠此判 `isOriginal` 根)→ 查不到「谁、何时、用什么 `field_mapping`/`doc_segment`、选了哪些快照」抽出来。彻底黑箱。

4. **成员级对应糊掉。** `JobInput` 是版本级;多表版本一进任务(`member_configs` 各成员跑不同算子链、其余 `carry_over_members` 带过),「输入哪个表→产出哪个表」的对应在版本边界丢失。

---

## 4. 阻断「可复现」的缺口

1. **LLM 任务不可复现(最严重)。** `engine.py:76`(`_subprocess_env`)与 `engine.py:197`(`build_config`)均在**任务执行时**调 `get_active_llm_config()`:算子的模型名(`cfg.model`)、`OPENAI_API_KEY`、端点全从**当前激活的 LLM 配置**现取,只有用户在表单显式填了 `api_model` 才进 spec。含义:
   - 重跑时激活配置若换了模型/端点 → 结果不同;
   - 无激活项时按 `refresh_cache` 逻辑**回退到最近一次配置的供应商** → 更不确定;
   - spec 里根本没有「用了哪个模型」这条信息。
   - 波及 `augment / trainset / distillation / review / judge`。

2. **出湖抽取步骤无法复现。** 无 Job = 无可重跑 spec;抽取用的 `field_mapping`/`doc_segment`/所选快照未作为可复现单元记录。

3. **算子代码/DJ 版本未固化。** spec 存算子名+参数,但自定义算子代码、DJ 本身版本会变,同名同参不保证同行为。(优先级低于前两项。)

4. **LLM 采样固有随机性。** temperature 等致即便模型固定也非逐行确定——改不了,产品上须诚实标注「生成类任务仅记录配方,不保证逐行一致」。

---

## 5. 整改方案(P0 → P2)

> 所有迁移仅在 **adp_gov** 库推进(`dbx` 连接 `PostgreSQL_adp_gov`),勿动 dev;alembic revision 名 ≤ 32 字符。

### P0-①:任务执行时固化 LLM 配置进 `Job.spec`(复现 #1)

- **改哪**:`engine.py` `build_config` / `_subprocess_env` 与各引擎入口。执行前把 `get_active_llm_config()` 解析出的 `{provider, model, base_url, extra_params}` **快照写入 `Job.spec.llm_snapshot`**;算子 `api_model` 自动填充改为「优先读 spec.llm_snapshot,其次现取」。
- **rerun**:`body_from_spec` 重建时若 spec 已有 `llm_snapshot`,直接用快照,不再现取激活配置。
- **验收**:改激活配置后 rerun 一个 augment 任务,子进程实际请求的 model/base_url == 首次执行时的值(查 `/llm-proxy/{job_id}` 计量日志核对)。

### P0-②:出湖抽取补建 Job(溯源 #3b + 复现 #2)

- **改哪**:`extract_to_new_dataset` 接线到已设计好但未接的 `extract_and_land_from_lake`(`lake_extract.py:293` 已接受 `produced_by_job_id`)。抽取时建 `Job(type="extract" 或 "ingest")`,`spec` 记 `{snapshot_ids, field_mapping, doc_segment}`,产出版本置 `produced_by_job_id`。
- **注意**:会改变 `isOriginal` 判据(现在靠 `produced_by_job_id is None` 判湖抽取根)。需同步改血缘 BFS:extract 边改为 `snapshot → extractJob → version`,`isOriginal` 改用「有无上游 JobInput/快照」判定。
- **验收**:抽取产出的版本能查到抽取 Job 及其参数;rerun 该 Job 用同样快照+映射产出等价版本。

### P1-①:入湖 Job 进血缘图 + 直连/媒体补写来源(溯源 #1 #2 #3a)

- 血缘 BFS 湖层:由 `snapshot.job_id` 补画 `ingestJob → snapshot` 节点/边。
- 直连/媒体路径:`add_table_member` / `land_media_manifest` 至少写一个来源占位(`source_kind ∈ {upload, push, manifest}` + 原始文件引用),让「从哪来」有答案。

### P1-②:血缘入口实体无关化 + member 提一等节点 +「任务资产清单」视图(溯源 #4 +「查全部资产」)

- 后端:把 `dataset_lineage()` 的 BFS 抽成 `lineage_service`,支持 `anchor={kind}:{id}` 任意实体作根 + 双向;`datasets/{id}/lineage` 保留为 thin wrapper。合并 `export_delivery.collect_lineage` 那份重复 BFS。
- member 由 version 节点的装饰 payload 升级为可展开子节点(数据现成:`member_configs` 有 per-member 算子、`source_snapshot_id` 有成员→快照边)。
- 前端:任务详情提供「资产清单」——输入版本+成员、算子链+参数、LLM 快照、上游快照/数据源、产出版本,一屏可见。

### P2:固化算子/DJ 指纹 + 诚实标注(复现 #3 #4)

- spec 记 DJ 版本 + 自定义算子代码指纹(hash)。
- 生成类任务 UI 标注「配方级复现,不保证逐行一致」。

---

## 6. 优先级与判定小结

| 优先级 | 事项 | 解决缺口 | 改动量 |
|---|---|---|---|
| **P0-①** | LLM 配置快照进 spec | 复现 #1 | 小 |
| **P0-②** | 出湖抽取补建 Job | 溯源 #3b + 复现 #2 | 中(动 isOriginal 判据) |
| **P1-①** | 入湖 Job 进图 + 直连/媒体补来源 | 溯源 #1 #2 #3a | 中 |
| **P1-②** | 血缘入口无关化 + member 一等节点 + 资产清单 | 溯源 #4 + 查全部资产 | 大 |
| **P2** | 算子/DJ 指纹 + 诚实标注 | 复现 #3 #4 | 小~中 |

**能否满足需求?——现在不能,但缺的都是「补记录 + 补节点」,不是推翻重来。** P0 两项(LLM 快照 + 出湖建 Job)是卡住「可溯源可复现」的两根钉子,改动可控,建议先行。
