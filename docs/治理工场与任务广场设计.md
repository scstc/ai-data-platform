# 治理工场与任务广场设计

## 背景

数据治理菜单下「数据清洗 / 数据蒸馏 / 数据合成 / 数据增强」四个模块目前是四份几乎相同的页面骨架:
各自独立的列表页(内嵌任务列表)+ 独立编辑器(算子选择 + 参数表单 + 试跑 + 提交),仅算子取用范围
(`bucket`)与提交端点(`/api/v1/{clean,distillation,make,augment}/jobs` 等)不同。复制粘贴带来两个问题:

1. **算子编排不可复用**:同一套"过滤脏字符 + 长度截断 + MinHash 去重"链路,用户每次新建任务都要
   重新勾选一遍算子和参数,无法存成模板跨数据集版本复用。
2. **四份代码维护成本线性叠加**:UI 改动(如新增筛选项、试跑交互)需要在四个页面同步修改,`docs/`
   历史整改记录里已多次出现"某场景漏改"的问题。

本次改造引入 **pipeline(流水线)** 作为一等公民:命名的算子编排,可保存、可复用、可在多个数据集版本
上重复执行;执行时落地为现有 `jobs` 表的一条记录(不改动 job 生命周期语义),仅新增 `pipeline_id`
回指关系,任务广场(`/ops/data-tasks`)据此追溯"这条任务是从哪个流水线跑出来的"。

算子编排器(`processing/editor/PipelineCanvas`,清洗编辑器与蒸馏/合成/增强共用的
`LlmScenarioEditor` 均复用同一组件)采用 xyflow 画布式交互:算子节点可在画布上自由拖拽摆放,
但连线被强约束为「输入 → 算子 → 算子 → … → 输出」单入单出的线性链——dj-process 执行引擎只认
线性算子序列,不支持分支或环路,故每个节点最多一进一出、连自环/成环均被拒绝,只能通过删边重连
调整执行顺序;未接入输入→输出主链的游离节点以红色虚线标出,提交或保存为流水线前会被拦截。

## Pipeline 数据模型与 API 契约

### 字段

```
PipelineRead {
  id: string
  name: string
  description?: string
  scenario: 'clean' | 'distillation' | 'synthesis' | 'augmentation'   // 与 Job.type 对齐
  spec: {
    operators: [{ name: string, params: Record<string, unknown> }]
    goal?: string        // 场景目标说明(合成/增强场景用于展示,不参与执行)
    textKeys?: string[]  // 清洗作用字段;留空由后端自动探测主文本字段
  }
  isPreset: boolean       // 预置模板:不可改名/编辑/删除
  createdBy: string
  createdAt: string
  updatedAt: string
}
```

### 端点

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/pipelines?scenario=&current=&pageSize=` | 分页列表(与现有 `PageResult` 结构一致);预置模板排在最前 |
| GET | `/api/v1/pipelines/{id}` | 详情 |
| POST | `/api/v1/pipelines` | 新建,body `{name, description?, scenario, spec}` |
| PUT | `/api/v1/pipelines/{id}` | 更新;预置模板返回 400 |
| DELETE | `/api/v1/pipelines/{id}` | 删除;预置模板返回 400 |
| POST | `/api/v1/pipelines/{id}/execute` | 执行,body `{name?, datasetVersionId}`;返回值与对应场景现有"新建任务"接口一致的 job item(含 `id`) |

前端 `src/services/data-platform` 对应函数名:`listPipelines` / `getPipeline` / `createPipeline` /
`updatePipeline` / `deletePipeline` / `executePipeline`;类型 `DataPlatform.Pipeline` /
`DataPlatform.PipelineSpec`,与现有 `DataPlatform` 命名空间下类型(`typings.d.ts`)同文件维护。

`JobRead`(及前端 `DataPlatform.Job`)新增可空字段 `pipelineId`:执行流水线产生的任务回填该字段;
手工编辑器直接新建的任务该字段为空,不强制要求"每个任务都必须来自流水线"。

## 执行链路:pipeline → job → 版本 / 血缘

```
流水线(pipeline, 可复用的算子编排)
   │ POST /pipelines/{id}/execute { datasetVersionId }
   ▼
任务(job, 落 jobs 表, job.pipeline_id = pipeline.id, job.type = pipeline.scenario)
   │ 现有 job 执行链路不变:dj-process 跑算子链 → 落新数据集版本
   ▼
数据集新版本(dataset_version, 血缘字段指向输入版本 + job_id)
```

- 流水线本身**不持有**执行状态,只是"配方";一次 `execute` 调用即对应现有各场景"新建并执行任务"
  接口的一次调用,返回值结构与之前完全一致(前端 job 列表 / 详情 / 血缘追溯代码零改动)。
- 任务广场(`/ops/data-tasks`)列表新增「来源流水线」列:`job.pipelineId` 存在时显示流水线名称,
  点击跳转回对应场景编辑器(`?pipelineId=<id>`)供查看/复用该流水线的算子配置;无流水线来源的任务
  (手工编辑器直接新建)显示 `-`。
- 血缘链路(数据源 → 数据湖 → 数据集版本 → 任务)不受影响,pipeline 只是任务的"上游配方来源"标注,
  不是血缘图的新节点。

## 分阶段清单

### 本期完成项

- [x] `pipelines` 数据模型 + 六个 CRUD/执行端点契约(见上)
- [x] `jobs` 表新增 `pipeline_id`,`JobRead` 暴露对应可空字段
- [x] 路由收口:`/governance/workbench` 主入口 + 四场景薄入口 + 四场景 `jobs` 隐藏路由
- [x] 前端 `DataPlatform.Pipeline`/`PipelineSpec` 类型 + 六个 API 函数
- [x] 任务广场「来源流水线」列(展示 + 跳转编辑器)

### 遗留项(本期不做,记录以便排期)

1. **LLM 场景预置模板**:当前 `isPreset` 模板仅覆盖规则类算子编排(清洗去重、格式过滤等);
   合成/增强场景常用的 LLM prompt 模板(如"基于种子问答生成变体")尚未沉淀为预置流水线,
   需要与 LLM 配置中心(`backend/app/services/llm_config.py`)联动设计参数占位符。
2. **抽样预览**:现有各编辑器的"样例试跑"(`POST /api/v1/jobs/preview`)尚未接入流水线维度——
   即"从流水线模板一键试跑"体验,目前仍需先执行、再看结果,缺少执行前预览。
3. **后端三 service 合并**:`distillation` / `make` / `augment` 三个场景当前分别有独立 service
   模块(创建任务、列表、详情、重跑各一套),字段与流程高度重复;治理工场统一入口上线后,
   具备把三者合并为一套"以 scenario 为参数"的通用 job service 的条件,本期未动以控制改动面。
4. **评标期薄菜单入口的撤除时机**:四个场景菜单项(`/governance/cleaning` 等)当前保留是为了让
   现有用户在评标/过渡期内仍可通过熟悉路径进入(内部只是预设了 `scenario` 的 Workbench);
   待使用数据显示用户已普遍改走"治理工场"主入口后,可评估收起为二级 Tab 或直接从菜单移除,
   仅保留路由重定向兜底旧书签。
