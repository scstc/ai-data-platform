# 数据湖文件版本模型整改设计

> 2026-07-04 · 治理整改（feature/governance-remediation-plan 分支，adp_gov 库验证）
> 状态：已实施（2026-07-04 迁移 0044 已在 adp_gov 执行并核验回填：48 快照 → 46 文件，object_id/version_no 全量回填无空洞；同日迁移 0045 补湖→仓血缘列，见 §5；dev 库 adp 未动）

## 1. 问题

现有湖模型只有两层：`DataLake` → `DataLakeSnapshot`，一条快照 = 一次入湖动作写入的一个对象（一张表 / 一个文件）。版本号 `source_v{日期}_{批次}_{类型}` 的批次号在「湖 × 当天 × source_type」维度自增（`data_lake.py::_next_batch_no`），既不代表"某文件的第几版"，也不代表"任务的第几次运行"。

后果：采集任务多次运行后，湖详情页是一坨平铺快照——

- 区分不了**同一个东西**：同一张表两次采集产生两条互不关联的快照，不存在"orders 表在湖里有 3 个版本"的概念；
- 区分不了**同一次运行**：一次任务采 5 张表 → 5 条快照批次号 01~05；每次运行有 `job_id` 但快照没记录。

## 2. 方案：两层改三层，快照变"文件的版本"

```
数据湖 DataLake
 └─ 文件 DataLakeObject（★新增：一张表 / 一个文件的稳定身份）
     └─ 版本 DataLakeSnapshot（该文件的 v1 / v2 / v3 …）
```

文件分两类（`origin` 列）：

- `ingested`：外部采集/上传进来的；
- `merged`：湖内合并生成的（多个结构化文件 union/join 成一个宽表文件）。

### 2.1 文件身份键 identity_key

采集/上传时按身份键查找文件：已存在 → 追加新版本；不存在 → 建新文件。

| 来源 | identity_key |
|---|---|
| 数据库表 | `{datasource_id}:{db_table}`（db_table 已含 schema 限定名） |
| 对象存储 / HDFS | `{datasource_id}:{bucket}/{obj_key}` |
| 本地上传 / API 推送 | `local:{original_filename}` |
| 湖内合并 | `merged:{用户命名}` |

### 2.2 表结构

**新表 `data_lake_objects`**：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | str PK | `lobj-` + uuid7 hex |
| `lake_id` | str | 所属湖 |
| `identity_key` | str | 身份键，`(lake_id, identity_key)` 唯一 |
| `display_name` | str | `public.orders` / `report.pdf` / 合并文件名 |
| `origin` | str | `ingested` \| `merged` |
| `data_category` / `storage_format` | str | 冗余自最新版本 |
| `latest_version_no` / `latest_snapshot_id` | int / str | 冗余，加速列表 |
| `merge_config` | JSONB null | 仅 merged：`{mode: union|join, join_keys, inputs: [{object_id, version_policy}]}` |
| `created_at` / `updated_at` | timestamptz | |

**`data_lake_snapshots` 加列**（存量先 nullable，回填后收紧）：

| 列 | 说明 |
|---|---|
| `object_id` | 属于哪个文件 |
| `version_no` | 该文件的第几版，`(object_id, version_no)` 唯一 |
| `job_id` | 哪次任务运行产出（手动上传/合并为空或记操作 job） |
| `merge_inputs` | JSONB，仅合并版本：`[{object_id, snapshot_id, version_no}, …]` 血缘 |

`source_version` 列保留兼容展示，语义降级为归档批次标签；判重主键从 `uq_lake_source_version` 让位给 `(object_id, version_no)`。

### 2.3 存储路径

```
旧：data-lake/{lake_id}/source_v20260704_01_postgresql/data.parquet
新：data-lake/{lake_id}/{identity_key 安全化}/v{n}/{文件名}
```

identity_key 安全化：非 `[A-Za-z0-9._-]` 字符替换为 `_`，超长截断 + hash 后缀。存量 MinIO 对象**不搬**（`storage_uri` 逐行记录，新旧并存）。

### 2.4 湖内合并（新功能）

- 仅对结构化文件（parquet 版本）开放；
- `union`：多文件纵向拼接（列并集，缺失补 null）；`join`：按键关联；
- 合并**只增不改**：产出 merged 文件的新版本，源文件不动；
- 重新合并：默认取各输入文件最新版，追加到已有合并文件（版本+1）或另存新文件——交互对齐「湖抽取生成数据集的新建/追加」（commit 3ff100b）；
- 每个合并版本记 `merge_inputs` 血缘，可回答"我由谁的哪版合成"。

### 2.5 前端

- 湖详情页主列表：快照流水 → **文件列表**（名称、origin 标、最新版本、版本数、最近归档、累计大小）；
- 文件点开 → 版本历史抽屉/子页（v1→vN：行数、大小、job、时间、下载）；
- 合并入口：勾选多个结构化文件 → 配置 union/join → 生成合并文件；
- 湖抽取选择器：从"选快照"升级为"选文件 + 选版本（默认最新）"；
- API 客户端手写进 `services/data-platform/api.ts`（**禁 `npm run openapi`**）。

## 3. 迁移与回填（仅 adp_gov）

1. Alembic 迁移（head 基于 `0043_review_finding_field`）：建 `data_lake_objects`，snapshots 加 4 列（nullable）+ 唯一/普通索引；
2. 回填（data migration，同迁移内或独立脚本）：按 §2.1 规则从 `source_metadata` 提取 identity_key，`(lake_id, identity_key)` 分组、组内按 `created_at` 排序编 v1..vn，插入对象行、回写 object_id/version_no；
3. 回填完成后 `object_id`/`version_no` 收紧 NOT NULL；
4. **只对 adp_gov 执行 upgrade**（`DATABASE_URL` 指向 adp_gov），dev 库 `adp` 不动；验证走 dbx（连接 `PostgreSQL_adp_gov`）。

已核实（2026-07-04，adp_gov 48 条存量快照）：`source_metadata` 形态与身份键规则完全吻合（local/api→`original_filename`；s3→`bucket_name`+`obj_key`；database→`db_table`），无脏数据阻碍回填。

## 5. 湖→仓结构化血缘（迁移 0045，2026-07-04 补）

湖抽取生成数据集原本只有两条弱血缘：记录级 meta（在 MinIO 数据文件里，SQL 查不到）
和版本 note 自由文本。反向溯源（"湖文件 X 的 v2 被抽到了哪些数据集"）实际不可用，
且 meta.version 存的 `source_version` 仅湖内唯一，跨湖有歧义。补两点：

1. **`dataset_version_tables` 加 `source_snapshot_id`**（弱引用无 FK + 索引
   `ix_dvt_source_snapshot`）：一个成员 = 一次快照抽取，正反向溯源均 SQL 可查，
   经 `snapshot.object_id/version_no` 定位"哪个湖文件的哪一版"。
   - `add_table_member` 新增同名参数；同名覆盖时血缘跟随新来源（非湖来源覆盖置空）；
     published→新 draft 的成员克隆随行携带；
   - 存量成员不回填（无可靠依据），留空表示"血缘未知"；
   - 多媒体路径（`land_media_manifest`）血缘仍断，属已知缺口，本期不做。
2. **记录 meta 补 `snapshot_id` 键**（全局唯一）：数据文件自含精确血缘，消除
   `source_version` 跨湖歧义。

正向查询示例（数据集成员 → 湖文件版本）：

```sql
SELECT dvt.table_name, dlo.display_name, dls.version_no
FROM dataset_version_tables dvt
JOIN data_lake_snapshots dls ON dls.id = dvt.source_snapshot_id
JOIN data_lake_objects dlo ON dlo.id = dls.object_id
WHERE dvt.dataset_version_id = :version_id;
```
